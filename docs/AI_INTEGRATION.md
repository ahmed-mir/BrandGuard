# Phase 5A — source-grounded AI advisory analysis

AI analysis is an optional, user-initiated aid. It is stored separately from deterministic `ReviewRun` and `ReviewFinding` records. It never changes a deterministic result, content workflow state, approval decision, current-approval validation, or TXT/PDF export eligibility.

## Provider and model

The adapter uses the official OpenAI Python SDK with provider-specific transports. OpenAI is the default provider and uses the Responses API with a strict JSON Schema response format; its model defaults to `gpt-5.4-mini`. Groq uses the OpenAI-compatible Chat Completions API at `https://api.groq.com/openai/v1`; its model defaults to `openai/gpt-oss-20b`. Groq receives the same strict BrandGuard schema using Chat Completions `response_format={"type":"json_schema","json_schema":{"name":"brandguard_advisory","strict":true,"schema":...}}`, `reasoning_effort="low"`, bounded `max_completion_tokens`, and `extra_body={"include_reasoning":false}`. The Groq-only reasoning inclusion flag is carried through SDK `extra_body`, not a direct SDK keyword. Both responses enter the same BrandGuard domain and evidence validators. SDK retries are disabled and configured timeout/output bounds apply to both. OpenAI sends `store=False`; this OpenAI-specific field is not sent to Groq. Provider retention terms and account controls differ and must be reviewed before external processing. See the [OpenAI Responses API text guide](https://developers.openai.com/api/docs/guides/text?api-mode=responses), [OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs), [Groq Structured Outputs guide](https://console.groq.com/docs/structured-outputs), [Groq reasoning guide](https://console.groq.com/docs/reasoning), [Groq API reference](https://console.groq.com/docs/api-reference), and [official Python SDK](https://github.com/openai/openai-python).

The model identifier is a provider configuration value, not an entitlement. The selected provider account must have API usage enabled, credits/quota and access to the chosen model. A ChatGPT subscription does not itself provide OpenAI API credits. Usage and account limits are provider-specific; verify them in the relevant provider console before enabling real requests.

## Configuration

AI is off by default. A configured key alone does not turn it on. The process needs all of:

- `BRANDGUARD_AI_ENABLED=true`
- `BRANDGUARD_AI_PROVIDER=openai` (default) or `groq`
- For OpenAI: `OPENAI_API_KEY`; optionally `BRANDGUARD_AI_MODEL` (defaults to `gpt-5.4-mini`)
- For Groq: `GROQ_API_KEY`; optionally `BRANDGUARD_GROQ_MODEL` (defaults to `openai/gpt-oss-20b`)

### Zero-cost Demo AI mode

`BRANDGUARD_AI_DEMO_MODE` is a separate, default-off flag. The hackathon demonstration configuration is:

```text
BRANDGUARD_AI_ENABLED=false
BRANDGUARD_AI_DEMO_MODE=true
```

No `OPENAI_API_KEY` is required. Demo mode builds repository-controlled sample advisories from the actual bounded, approved LumaDesk source passages retrieved for the current workspace and content. It does not call the real provider adapter or import the OpenAI client. The simulated output still passes through the normal server-side schema, content-span, source, snapshot, and exact-evidence validation before findings are saved. Runs are stored with provider `demo` and model `simulated-brandguard-demo`, and external-provider consent fields remain false/empty. The user explicitly confirms that the simulation is not a provider response before running it.

The version page displays **Demo AI mode** and the disclosure **“Simulated advisory analysis for demonstration purposes. No external AI provider is contacted.”** The action is labeled **Run demo AI analysis**. Every saved demo run repeats the simulated/no-provider disclosure. The demo output is illustrative and is not generated by a language model. It cannot alter deterministic checks, workflow state, approvals, or export eligibility.

Never enable both `BRANDGUARD_AI_ENABLED` and `BRANDGUARD_AI_DEMO_MODE` together. The application treats this as an ambiguous configuration, shows AI unavailable, and rejects the request before either adapter can run. To return to the existing AI-unavailable behavior, set both flags to `false`.

Optional bounded controls:

| Variable | Default | Enforced range |
|---|---:|---:|
| `BRANDGUARD_AI_TIMEOUT_SECONDS` | 15 | 3–20 seconds |
| `BRANDGUARD_AI_MAX_OUTPUT_TOKENS` | 1,400 | 100–2,000 |
| `BRANDGUARD_AI_MAX_FINDINGS` | 12 | 1–12 |
| `BRANDGUARD_AI_MAX_CONTEXT_CHARS` | 10,000 | 1,000–12,000 |

Marketing content is already limited to 20,000 characters by the content-review form and model. The synchronous timeout is 15 seconds by default, below the app's Gunicorn request timeout. The SDK retry count is zero. Configure these variables in Render's secret/environment settings only when intentionally enabling the feature. Never put the API key in source control, this document, the browser or a logged command.

For local PowerShell, after adding the key to a trusted local secret manager/process environment, load it into this shell without printing it, then opt in for that process:

```powershell
$env:OPENAI_API_KEY = [Environment]::GetEnvironmentVariable('OPENAI_API_KEY', 'User')
$env:BRANDGUARD_AI_ENABLED = 'true'
$env:BRANDGUARD_AI_MODEL = 'gpt-5.4-mini'
python manage.py runserver
```

For a deliberately authorized Groq test, set the selector/model and opt-in controls in the local process environment, then make the key available through a trusted secret manager or the parent shell without printing it:

```powershell
$env:BRANDGUARD_AI_ENABLED = 'true'
$env:BRANDGUARD_AI_DEMO_MODE = 'false'
$env:BRANDGUARD_AI_PROVIDER = 'groq'
$env:BRANDGUARD_GROQ_MODEL = 'openai/gpt-oss-20b'
$env:BRANDGUARD_AI_TIMEOUT_SECONDS = '15'
$env:BRANDGUARD_AI_MAX_OUTPUT_TOKENS = '1000'
$env:BRANDGUARD_AI_MAX_FINDINGS = '3'
$env:BRANDGUARD_AI_MAX_CONTEXT_CHARS = '4000'
python manage.py runserver 127.0.0.1:8000
```

Set `GROQ_API_KEY` only in that local process environment; never type its value into source-controlled files or a logged command. The experimental Groq Responses transport failed in two separately authorized attempts, including an HTTP 400. The current Chat Completions path has since completed one separately authorized synthetic BrandGuard analysis locally. Its strict response, domain validation, evidence grounding, provider/model persistence, and isolation from deterministic review and approvals/exports all passed. This does not establish OpenAI live access or deployment of this unpushed code.

If both flags are false, or real mode is enabled without a key, the page shows an honest unavailable state and deterministic review continues normally.

## User consent and transmitted information

The creator must submit a CSRF-protected POST and check an explicit disclosure on the exact content-version page. Normal page viewing never calls the provider. The disclosure states that selected marketing copy and relevant approved excerpts leave BrandGuard for the requested analysis.

For one request, the provider receives:

- The exact saved marketing text for the selected immutable `ContentVersion` (max 20,000 characters).
- Channel, optional audience and campaign purpose.
- A bounded lexical selection of exact passages (max 10,000 characters by default) from currently approved, currently effective source versions in the resolved workspace.
- The provided source-version IDs, source titles and version numbers used to make citations possible.

It does not receive raw uploaded files, draft/superseded/future-effective/cross-workspace sources, database rows, credentials, account identity, tools or a web-search capability. The user must have authority to send that content and source material to the provider. The synthetic LumaDesk pack is recommended for demos.

The OpenAI request uses Responses `store=False`. This is not a promise of zero provider retention; operators must review that provider's account controls and terms before sending confidential data. Groq receives no `store` field because that OpenAI-specific option is not part of the request shape used here. Review Groq's applicable retention, data-use and account controls separately. Never assume provider data handling is identical across providers.

## Snapshot and bounded context

The service resolves membership from the authenticated server-side workspace. It captures `policy_snapshot(workspace)` and the exact effective approved source version set while briefly locking the workspace row used by policy publication. It releases database locks before making the network request. It uses bounded lexical retrieval over source text and gives explicit voice-rule passages priority. There is no vector store and no external search.

The persisted `AIAnalysisRun` records the workspace, exact immutable content version/hash, policy revision/hash/full snapshot, the bounded context manifest (exact approved passages sent), requesting user, provider/model, consent timestamp, status, error category and token usage when returned. It does not persist the full prompt, complete provider response, duplicate copy of the submitted text, or private uploaded files. Each finding links to its source version and source-content hash when it is evidence-backed. Results for a content version or policy snapshot that is no longer current remain available as historical advisory results and are visibly marked stale.

## Output schema and validation

The provider receives a strict JSON Schema with a `findings` array. Each finding has only `category`, `classification`, `explanation`, `matched_text`, `source_version_id`, `evidence_excerpt` and `suggested_wording`; extra properties are rejected. Supported categories are `TONE`, `MESSAGING` and `CLAIM`. Classifications are `SUPPORTED`, `POTENTIAL_CONFLICT`, `NOT_VERIFIED` and `NEEDS_HUMAN_REVIEW`.

The server validates the schema again, allowed categories/classifications, field lengths, finding count, workspace, version identity, snapshot membership, approved source hash, and that the exact quoted evidence occurs both in the immutable source text and in a passage actually sent to the provider. Tone and messaging findings must be marked as potential conflict or human review and cite an approved excerpt. A claim may be uncited only when it is classified `NOT_VERIFIED` or `NEEDS_HUMAN_REVIEW`; the interface clearly says that absence of evidence does not establish falsity. Invalid source IDs/evidence fail the run and no finding is stored. Suggested wording is rejected if it adds a number not present in its cited excerpt.

Prompt injection is treated as untrusted text. System instructions are separate from JSON-encoded content/source passages and explicitly prohibit following instructions within that data. The model has no tools or external actions. Strict JSON is not treated as a prompt-injection defense by itself; server validation remains authoritative.

## Deterministic versus AI results

Deterministic `ReviewRun` checks are objective executions of persisted typed rules and remain the basis for the existing content review workflow. AI analysis is separately identified, subjective and advisory. An AI finding cannot become a deterministic rule finding, human approval, high-severity override, or export authorization. AI analysis is not included in the approved-content PDF report in this phase.

## Failure behavior and cost controls

The stored run state is `RUNNING`, then `COMPLETE` or `FAILED`. No provider request results in a success-shaped response. Failures use non-sensitive categories for disabled/missing configuration, no approved context, application rate limit, timeout, authentication, quota, provider rate limit/unavailability, refusal, invalid response/evidence, stale references or persistence failure. The UI preserves deterministic results and says AI had no effect on them. Error logs contain record IDs and exception class only; no content, source excerpt, API key, response body or request headers.

At most three analysis attempts per requesting user/content version in a rolling hour are permitted. A completed analysis with the same content hash, exact policy snapshot, provider and model is reused instead of billed again. An equivalent recent in-flight request is also reused, including when separate tabs have different request tokens; its request is bounded by the configured provider timeout. OpenAI and Groq runs, and different model identifiers, are not conflated. Old in-flight records beyond that timeout window do not block a retry after an abnormal worker exit. New content or policy identities allow a new separately recorded analysis. No automatic reruns occur. Provider account spend limits should also be configured by the operator.

## Data model and migration

The new `ai_analysis` app stores `AIAnalysisRun` and `AIAnalysisFinding` separately from deterministic review records. Findings are immutable and their content offsets are derived and checked against the exact saved version. Evidence fields can only refer to an approved source version in the saved policy snapshot/context manifest. No change is made to approval or export models/services.

Apply local migrations with `python manage.py migrate`. To disable real provider requests, set `BRANDGUARD_AI_ENABLED=false`. To make all analysis unavailable, set both `BRANDGUARD_AI_ENABLED=false` and `BRANDGUARD_AI_DEMO_MODE=false`. The deterministic review, approvals and exports continue. The migration may remain in place; do not delete AI analysis history as part of an emergency disable. Rolling back app code after data has been written requires a normal Django migration review and backup; do not reverse migrations blindly.

## Known limits

- Tone and contextual messaging are subjective and can be wrong; a cited passage shows what was supplied, not that the judgement is objectively true.
- No internet fact checking, broad factual validation, calibrated confidence, semantic rule execution, image/OCR, poster, audio or video analysis is implemented.
- Lexical retrieval can miss relevant guidance; the analysis is limited to the excerpts saved in its context manifest.
- AI analysis has no effect on the approval workflow. Human approval remains the only approval authority.
- A controlled OpenAI Responses API request was rate limited; no retry was made, and OpenAI live success has not been established. Two earlier Groq Responses API attempts failed without saving findings. A later single Groq Chat Completions request completed through BrandGuard with strict schema, domain, and evidence checks passing; two findings were saved, and deterministic review and approval/export state remained unchanged. Automated provider tests remain mocked. Provider availability, model entitlement, account retention settings and billing are operator-side concerns. Demo AI is simulated repository-controlled output and must never be represented as a live model response.
- The zero-cost Demo AI path is not a substitute for provider validation. It is a small deterministic example generator, clearly identified as simulated, with all citations rechecked against the saved policy snapshot and exact source text.
- SQLite tests do not establish PostgreSQL multi-writer concurrency. The brief's current optional feature is synchronous and short; it uses the PostgreSQL-compatible workspace row-lock snapshot pattern, but a live PostgreSQL AI-request test remains to be performed before enabling it broadly.
